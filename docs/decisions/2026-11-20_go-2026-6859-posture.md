# Owner Decision — GO-2026-6859 posture (2026-11-20, T07)

**Decision: HOLD red until nixpkgs ships go 1.27.4; the flake-level
override is REJECTED.** Recorded under the 2026-11-20 execution order

## The vulnerability

GO-2026-6859 — "HTTP/1 server crash due to MaxBytesReader header race in
net/http". Found in `net/http@go1.27.3` (what nixpkgs `go_1_27` ships
today), fixed in `net/http@go1.27.4`. govulncheck flags REACHABLE traces
(the lens is an HTTP/1 server: `telnyx.Client.get` → `http.Client.Do`,
export CSV writes, OIDC userinfo calls — verified 2026-11-20, run under
nixpkgs go 1.27.3).

## Why HOLD (and not an early override)

1. **Doctrine:** the flake builds hermetically from nixpkgs; a
   hand-patched stdlib forks the toolchain the fleet's lint/gopls pins
   are built against (docs/gotchas.md § "The flake hardening contract").
2. **The CI lane is NOT exposed:** GitHub Actions' `setup-go` resolves
   `GO_VERSION: 1.27` → go1.27.4 already (observed on run 44713670130),
   so the Vulnerability Check lane runs the patched toolchain today.
3. **Exposure is LAN-only, single operator** — the crash needs a crafted
   HTTP/1 request stream aimed at the lens; the operator's own LAN is
   the only client population.
4. **The fix is one eval away:** when `nix eval nixpkgs#go_1_27.version`
   prints ≥ 1.27.4, bump the flake input + the go.mod floor IN ONE
   change (F21/F22), then `nix develop -c govulncheck ./...` must print
   zero findings (F23) and the vendorHash re-verifies (go.mod floor
   changes the module graph? No — the floor is a `go` directive;
   vendorHash unchanged, but `nix build` proves it).
