01Type-safety concerns

F1 — Single-flight hands concurrent waiters a zero-value result (crash)

internal/oidclogin/oidclogin.go:421-460. providerFor's handoff channel is buffered 1: the discoverer sends one providerResult then closes. Go semantics: the FIRST waiter receives the real result; every additional waiter blocked on <-ch receives the CLOSED-channel zero value {p: nil, err: nil}. That is a nil provider reported as success — begin() (line 204) immediately calls provider.Endpoint() on it → nil-pointer panic in the serve goroutine. Worse: when discovery FAILED, extra waiters get {nil, nil} — the failure is masked as success for everyone but the first caller. The Provider doc (line 112) claims "Safe for concurrent use", and oidclogin_test.go has no concurrent-discovery test, which is why this survived. 

// current shape (oidclogin.go:430-437)
if p.inflight != nil {
    ch := p.inflight
    p.mu.Unlock()
    res := <-ch          // 2nd waiter: closed channel → {nil, nil}
    return res.p, res.err // nil, nil — "success"
Fix Make waiters loop: after <-ch, re-lock and re-check p.oidcProv/err state; if still empty (failed discovery), retry the discovery yourself (failures are deliberately not cached). Alternative: replace the channel with a sync.WaitGroup + result fields guarded by the existing mutex. Add a regression test: stub IdP, 8 goroutines calling providerFor concurrently against a cold cache — all must get the provider or the SAME error, none a nil-nil pair.

F3 — Enrich's observation parameter is dead: a lying signature

internal/calls/decider.go:146 takes Enrich(obs Observation, enr Enrichment, streamID), but the body (line 174) emits CallEnriched{Observation: state.Current, ...} — the parameter is silently discarded. The one production caller (internal/app/app.go:60) passes cmd.Observation, and EnrichCallCmd (commands.go:38-43) carries an Observation field whose only real job is addressing. Today state.Current and cmd.Observation coincide by construction (the enrich pass rebuilds the observation from the view), so this is latent, not live — but any future caller passing a fresher snapshot gets the stale one with no signal. Type-safety rule: a parameter the callee ignores should not compile into the contract.

Fix Drop the obs parameter from calls.Enrich (the state owns the observation), update app.go and scenario_test.go call sites. If the pairing must stay, validate it (state.Current.ContentHash() != obs.ContentHash() → Corruption rejection) so the lie becomes a guarded invariant.

F13 — Redundant explicit type arguments

internal/app/app.go:44, 54, 64 — system.RegisterCommand[calls.X, calls.CallState] infers both parameters; gopls infertypeargs flags all three. Cosmetic, but it suggests the call is more ambiguous than it is.

F2 — Three read sites bypass calls.LookupView against the stated doctrine

AGENTS.md: "Projection record keys are BARE … read through calls.LookupView (its marker-prefixed fallback keeps pre-flip rows reachable)". refresh.go and agent.go honor it; these don't:

SiteEffect on legacy-keyed rows
internal/cli/ingest.go:50 supersedes stays false → a correction reports as "recorded" in IngestStats
internal/cli/enrich.go:82 found=false → the stream counts Missing EVERY pass; enrichment never lands
cmd/pbx-lens/ops.go:85 (smoke) benign today (fresh bare keys), same shape — align while touching the file

The enrich site is the meaningful one: until the one-time rebuild (blocked TODO row) runs, every pre-2026-10-23 Telnyx stream retries Missing forever and its cost/insight never arrives. refresh.go:107's comment explicitly calls out this exact trap — the doctrine and the code disagree inside one package.

Fix ingest.go: replace the bare reader.Get(ctx, calls.RecordKey(...)) with calls.LookupView(ctx, reader, cmd.StreamID()). enrich.go: keep EnrichmentSeed.StreamKey for the SeedsFor set-intersection but resolve the read through LookupView (store the StreamID, or parse it from the seed). Add a test: write a legacy-keyed row (via LegacyRecordKey), run Ingest with a changed hash → Corrected (not Recorded); run the enrich pass → enriches (not Missing).

F6 — weekDelta comment vs the 7-day preset (doc drift with UI impact)

internal/web/dashboard.go:389-390 says "The window is always 30 days" — but ?window=7 (server.go:485-500) feeds DashboardStatsQuery a 7-day ByDay, so weekDelta, costWeekDelta, and qualityTrend all need len(days) ≥ 14 and silently render HasBaseline=false on the 7-day preset. The comment and the code disagree; the operator sees deltas vanish with no explanation.

Fix Either scan a floor-14-day window for the delta inputs regardless of chart window, or fix the comment and have the 7-day preset hide the delta cards explicitly ("needs a 30-day window"). Pick one truth.

F9 — Webhook hangup-cause fold breaks the claimed order-independence

internal/ingest/webhook/webhook.go:130-132: foldPayload is first-non-empty-wins (line 137), but the cause assignment directly above it is LAST-non-empty-wins. The Parse doc (line 57-58) promises "the aggregation is order-independent so the ContentHash is stable". Two DIFFERENT non-empty hangup causes sharing one call_control_id (a-leg/b-leg split) would produce different hashes under different line orders — the exact correction-churn class the invariant exists to prevent. Today's traffic has one cause per call_control_id, so it's latent.

Fix Move the cause into foldPayload with the same first-wins guard; extend TestParseOrderIndependent with a fixture carrying two distinct causes in both orders asserting one hash.
