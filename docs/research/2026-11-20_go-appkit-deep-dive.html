00Summary

go-appkit owns the entire HTTP shell of serve: listener, default middleware stack, health/version/metrics endpoints, signal handling and graceful drain. Usage was re-verified at HEAD (2026-11-20) against the pinned v0.12.0 source: every applicable capability is in use, and the 2026-11-12 v0.12 bump removed pbx-lens code (the explicit Server-Timing middleware wiring) rather than adding any. 21 capability rows were graded: 12 applicable, all fully leveraged; 9 documented non-adoptions with reasons.

This report applies the deep-dive rubric as written — documented non-adoptions are Not Applicable, excluded from the denominator — and re-verifies that nothing new opened. One real usage delta exists since the fleet scored: ReadyCheck was wired (plan T17, serve.go:208-214), one of the fleet's unwired rows. The used surface is otherwise unchanged; the honest reading is “nothing left to adopt that applies.”

01Findings

No Misused and no applicable Missed findings. The named trap classes were checked explicitly: Health/version/metrics routes are appkit-canonical (auto-registered, no hand-rolled equivalents); the Server-Timing mount is the v0.12 default with zero duplicated wiring; no explicit timing middleware remains anywhere in serve composition. What is left is one pin lag and three documented non-adoptions worth restating with their reasons.

Version currency · Low impact

systemd pin v0.1.0 is one minor behind — v0.2.0's Hooks return is source-compatible and deliberately unwired

go.mod:12 · library: go-appkit/systemd CHANGELOG (v0.1.1 2026-11-07, v0.2.0 2026-11-08)

v0.1.1 is docs-only (runnable Examples, README truth). v0.2.0 changes Install to return the wired Hooks value so a start path that fails AFTER StartHooks can stop the watchdog keepalive. pbx-lens' failed-start path is fatal() — process death stops the keepalive — so the return value is deliberately ignored; existing Install(&cfg) call sites compile unchanged. Root module v0.12.0 is the latest tag; upstream root [Unreleased] carries only repo-CI lint changes (consumer- irrelevant).

Recommendation Ride systemd v0.1.0 → v0.2.0 on the next deps train (tidy may pick it up automatically alongside any appkit move). No code change needed; the Hooks return stays unwired unless a non-fatal start-failure path ever appears.
Fully used, with a nuance worth knowing · Low impact

Two SecurityHeaders middlewares run in the chain — by design, and it is the only sanctioned path

cmd/pbx-lens/serve.go:386-398 · appkit@v0.12.0 config.go:61-65, middleware.go:29-64

The default stack ends with appkit's SecurityHeaders; pbx-lens appends its own httputil.SecurityHeaders as an extra to set nosniff, no-referrer and X-Robots-Tag — headers the default does not carry and whose values ServiceConfig cannot configure. The inner Set calls win; the default's X-Frame-Options: DENY survives. Replacing the stack via Middlewares would drop ServerTiming/Recovery/ RequestID/Logging — strictly worse. This is the library's intended extension shape, recorded here so a future reader does not “deduplicate” it into a regression.

Not applicable, reason recorded · Low impact

Lifecycle hooks (Start/Drain/Shutdown) have exactly one consumer: systemd.Install

serve.go:380 (Install) · openServeIndex closeAll at serve.go:478-484

The remaining hook families stay unwired for recorded reasons: dependencies open before the listener binds (nothing to announce in StartHooks beyond what systemd already does), and teardown rides defer closeAll() because the FTS index must close BEFORE the CQRS system releases the journal — a ShutdownHook runs after server connections release but the defer ordering is the load-bearing contract, and appkit hooks cannot express index-before-system ordering against resources appkit does not own. Revisit only if a hook-shaped need (telemetry flush, external readiness signal) actually appears.

Not applicable (no-op verdict) · Low impact

testkit helper family (WaitForRunning/FreeAddr/HTTPGetURL/DrainWindowProbe): adopted as a no-op

cmd/pbx-lens/serve_test.go:59-63,188-199,300-311 · testkit/httptest.go:22-96

The 2026-11-12 refresh verdict stands: pbx-lens' boots already use the modern NewService+Serve pattern with ephemeral addresses and auto-wait; swapping in FreeAddr/WaitForRunning would be cosmetic churn with no behavioral claim to pin. DrainWindowProbe would matter only if a drain-window regression test is ever wanted.
